# DECISIONS — решения и допущения

Сюда записываются вопросы, на которые задание не отвечает, и принятые решения. Потом это войдёт в README.
Статус: ❓ открыт (есть только рекомендация) · ✅ принято

## Допущения по бизнес-логике

| # | Вопрос | Рекомендация | Статус |
|---|--------|--------------|--------|
| 1 | Существующий username + неверный пароль | 401 | ✅ |
| 2 | Ограничения на username/password (длина, символы, пустые) | Непустые; username до 64 символов; пароль до 72 байт (лимит bcrypt) | ✅ |
| 3 | Перевод несуществующему пользователю | 400, автосоздание не делаем | ✅ |
| 4 | Перевод самому себе | 400 | ✅ |
| 5 | `amount <= 0` | 400 | ✅ |
| 6 | «Сгруппированная» история: каждый перевод отдельно или сумма по пользователю | Сумма по каждому контрагенту (`GROUP BY`): так понятнее слово «сгруппированная», и ответ меньше | ✅ |
| 7 | Попадают ли покупки в `coinHistory` | Нет, только переводы; покупки видны в `inventory` | ✅ |
| 8 | Сколько штук покупается за один `/api/buy` | Одна | ✅ |
| 9 | Код ответа при нехватке монет / неизвестном товаре | 400 (других кодов в схеме нет) | ✅ |
| 10 | Время жизни JWT | 24 часа, refresh-токены не делаем | ✅ |
| 11 | `/api/buy` — это GET, хотя он меняет состояние | Оставляем GET, потому что так в контракте; в README отметим, что по REST здесь был бы POST | ✅ |
| 12 | Каталог мерча меняется? | Нет, 10 позиций, запас бесконечный | ✅ |
| 13 | Порядок элементов в `inventory` / `coinHistory` | Детерминированный (по имени), чтобы тесты не флакали | ✅ |

## Технические решения

| # | Вопрос | Варианты | Статус |
|---|--------|----------|--------|
| T1 | Архитектура | Три слоя handler → service → repository; интерфейсы объявлены на стороне потребителя (в service); моки генерирует mockery. Clean/Hexagonal отклонена: для 4 ручек это лишний шаблонный код | ✅ |
| T2 | Роутер | Стандартный `net/http` (паттерны Go 1.22+): без зависимостей, хватает для 4 ручек | ✅ |
| T3 | Драйвер БД | `pgx/v5` + `pgxpool` | ✅ |
| T4 | Транзакции через слои | Свой минимальный transaction manager: tx передаётся через `context`, service вызывает `tm.Do(ctx, fn)`. Можно позже заменить на avito-tech/go-transaction-manager | ✅ |
| T5 | Защита баланса | условный атомарный UPDATE / `SELECT ... FOR UPDATE` / SERIALIZABLE + ретраи | ❓ |
| T6 | Мерч: таблица в БД или константа в коде | Таблица `merch` (`name UNIQUE`, `price > 0`), заполняется в миграции. `inventory` ссылается на неё через FK, поэтому записать несуществующий товар нельзя; цена берётся в SQL внутри транзакции покупки. Каталог не меняется (решение 12), поэтому при необходимости можно закешировать его в памяти (этап 8) | ✅ |
| T7 | Инвентарь: лог покупок или счётчик (user, item, qty) | Счётчик `inventory(user_id, merch_id, quantity)`, составной PK `(user_id, merch_id)`. Ответ `/api/info` берётся без `GROUP BY`, покупка — один upsert `INSERT ... ON CONFLICT DO UPDATE SET quantity = quantity + 1`. PK заодно даёт индекс по `user_id` | ✅ |
| T8 | Миграции | golang-migrate, SQL-файлы в `migrations/`, отдельный сервис `migrate` в compose: `db` (healthy) → `migrate` (completed) → `shop`. Сервис сам не мигрирует: нет гонки миграций при нескольких репликах, приложению не нужны права на DDL | ✅ |
| T9 | E2E-окружение | docker-compose.e2e.yaml / testcontainers-go | ❓ |
| T10 | bcrypt cost | | ❓ |
| T11 | Конфигурация | `caarlos0/env`, вложенные структуры (Server / DB / JWT); `JWT_SECRET` обязателен, без него сервис не стартует | ✅ |
| T12 | Секреты при запуске через compose | `env_file: .env`, переменные Postgres подставляются из того же `.env` через `${...}`. `.env` не коммитится, проверяющий делает `cp .env.example .env` (будет в README). Дефолтные секреты в compose отклонены: не приучаемся коммитить секреты | ✅ |
| T13 | Docker-образ | Multi-stage: `golang:1.27` → `distroless/static:nonroot`, `CGO_ENABLED=0`, `ENTRYPOINT` в exec-форме (чтобы SIGTERM доходил до процесса). Образ ~20 МБ. `stop_grace_period: 15s` > `SERVER_SHUTDOWN_TIMEOUT` | ✅ |
| T14 | Гонка первой регистрации в `/api/auth` | Репозиторий: `INSERT ... ON CONFLICT (username) DO NOTHING RETURNING ...`; если строки нет (`pgx.ErrNoRows`), возвращается `domain.ErrUserExists`. Сервис на `ErrUserExists` перечитывает пользователя и сверяет пароль, поэтому два одновременных первых входа не дают 500. Стартовый баланс задаёт только `DEFAULT 1000` в схеме, приложение `balance` в `INSERT` не передаёт (один источник правды) | ✅ |
